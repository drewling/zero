# Slice 01: ten references and a replacement design direction

## Owner's brief

The user rejected the entire visual design after seeing the live screenshots and asked for `/impeccable`, Claude Opus 5.5 to design in this seat, and ten references of Linear.app quality. Interpret Linear as **craft bar**, not as an instruction to clone its dark palette, typography or layout. Existing departure-board design is an anti-reference. The owner wants a visibly better, unmistakably zero site.

## Work

1. Use `/impeccable` replacement-world flow. Audit live `zero.headless.com` and its actual visitor journey and critique the current design with concrete, screenshot-grounded observations. Preserve product truth, safety disclosures, actual app image and working install/legal paths. You may change copy hierarchy, palette, type, layout, motion and graphic language.
2. Find **ten** live, distinct, high-craft product/technology sites. For each give URL, inspection date, real screenshot or visual observation, one transferable craft principle and one thing not to imitate. Include Linear.app as a calibration reference only if actually inspected. Cover more than ten instances of one dark SaaS template. Cite source pages. Browser use for visual inspection is warranted because screenshots and layout cannot be verified through text alone; use `/aside` as configured. Discover candidate URLs through search if useful.
3. Derive materially different, product-specific design directions using impeccable's concept-seed flow, not a single palette swap. Present owner-facing viewable desktop and mobile **visual comps** for the leading direction and credible alternative(s), first viewport and representative downstream section, including motion role and graceful reduced-motion/static state. Make them visually honest about the real app and install path.
4. Deliver a concise design brief, ten-reference atlas and viewable artifacts under `proof/`. State rationale, risks, what differs from rejected design, what remains truthful, and the exact owner decision needed. No `landing/` production edits, build dispatch or deploy until owner sees and approves direction.
5. Include a replacement inventory for handoff: which old page components, styles, Canvas/animation code and assets should be removed versus which product content, app imagery and infrastructure routes must survive. The owner wants a clean replacement, not a skin atop the departure board. Do not delete or edit production code in this slice.

## Proof/acceptance

- [x] Ten inspected URLs with dated evidence and useful distinct lessons, not a list of names.
- [x] Existing live page audit grounded in screenshots and user feedback.
- [x] Viewable distinct replacement comps at desktop and mobile, including an accessible/static state, with direct artifact paths.
- [x] Owner-facing recommendation and explicit request for visual choice, handed to `main-lead@zero` through durable queue.
- [x] Explicit keep/replace/remove inventory that prevents legacy code from accumulating in implementation.
