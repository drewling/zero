# Speed plan: corrected evidence and execution record

Updated 2026-09-18. This replaces the unsupported diagnosis and latency forecasts
in the original plan. Implementation was evaluated against offline fixtures and
local transports. **No live archive, send, label mutation, or mailbox benchmark
was performed. No vendor messages or credentials were exported.**

## Corrections to the original plan

1. **An empty checkout cache does not diagnose the installed app.** The clean
   source checkout began at `2160bb5`. The coordinator checked aggregate installed
   runtime state under `~/Library/Application Support/zero/app/thread_cache`:
   one JSON file, 14 thread entries, 13 sender entries, 14 verdicts. The checkout
   had no cache JSON files. Persistence was therefore working in at least that
   installed runtime. These counts do not establish hit rate or a performance
   problem. No private entry contents are included here.
2. **Triage learning is not all generated by an LLM.** `learn.py` builds restore
   and recurring-archive preference sections deterministically. Only draft voice
   is generated through the configured text provider. Regenerating voice can
   change learned text, but a universal nightly invalidation cycle was not
   measured. Counts of edits/restores are not a safe cache key.
3. **Separate users have separate user quotas.** The provider also applies a
   shared project limit. Two independent accounts do not each spend the same
   user's quota simply because they run concurrently. Same-account processes,
   shared state files, and shared project limits remain real coordination issues.
4. **A 0.42-second getProfile observation is end-to-end latency, not pure CLI
   overhead.** It can include process startup, authentication, DNS, connection
   establishment, service latency, and output handling. Neither that sample nor
   the claimed 70 ms startup component was re-benchmarked here.
5. **Quota units are not elapsed seconds.** Method costs below are verified, but
   dividing units by a minute budget gives budget consumption, not guaranteed
   wall time or pure waiting. Initial sliding-window capacity, other callers,
   concurrency, API latency, retries, and workload shape matter. The previous
   20x, 13-second, 20–40-second, and 6.5-to-6.4-minute promises are withdrawn.
6. **Newest-message metadata is not full-thread metadata.** Catch-up checks every
   sender in the conversation. Dashboard needs dates and label information.
   The existing classifier cache cannot simply replace their `threads.get`
   calls without losing inputs.
7. **Mailbox history alone does not validate decisions.** An unchanged thread
   can need a new decision after a policy, category, learned-preference, model,
   threshold, or sender-history change. The old history-only candidate narrowing
   bypassed verdict fingerprint checks. This was a correctness gap, not evidence
   that the cache was broken.

## Provider evidence, checked 2026-09-18

Public Google documentation was read through the approved Aside workflow. No
account mailbox or authenticated account data was accessed for this research.

- [Quota reference](https://developers.google.com/workspace/gmail/api/reference/quota):
  6,000 units/minute/user/project and 1,200,000 units/minute/project.
- [threads.list](https://developers.google.com/workspace/gmail/api/reference/rest/v1/users.threads/list):
  default 100, maximum 500 results per request. A request is not free.
- [Thread resource](https://developers.google.com/workspace/gmail/api/reference/rest/v1/users.threads):
  `historyId` identifies the last history record modifying the thread. The list
  method returns Thread resources without messages. Do not assume a history ID
  is always supplied: all reuse paths require a nonempty observed ID and miss
  when it is absent. A mailbox-wide getProfile ID is not a per-thread version.
- [history.list](https://developers.google.com/workspace/gmail/api/reference/rest/v1/users.history/list)
  and [synchronization guide](https://developers.google.com/workspace/gmail/api/guides/sync):
  outdated history IDs typically yield 404 and require full synchronization.
  History commonly lasts at least a week, but can expire within hours. The local
  five-day age cutoff is only a conservative heuristic, not a validity guarantee.

| Method | Units per API request |
|---|---:|
| `getProfile` | 1 |
| `history.list` | 2 |
| `labels.list` | 1 |
| `messages.list` | 5 |
| `messages.get` | 20 |
| `messages.batchModify` | 50 |
| `threads.list` | 10 |
| `threads.get` | 40 |
| `threads.modify` | 10 |

The transport now uses the shared `gmail_quota.UNIT_COSTS` table. **4,800
units/minute is this application's conservative local budget**, not a distinct
provider limit. Metrics report estimated client charges, not Google's billing
ledger. Unknown Gmail methods use a conservative fallback. People API calls are
not charged as Gmail. Bulk `--page-all` reads report observed pages and estimated
units separately from subprocess count.

## Implemented

### 1. Observable cost without private mail in metrics

`lib/run_metrics.py` records stage/process elapsed time, API attempt durations,
pseudonymous account IDs, estimated Gmail units, throttle duration, retries,
transport/command failures, cache hits/misses, category no-ops, learning reuse,
and Jev connection creation/reuse. Metrics do not contain message IDs, addresses,
paths, bodies, subjects, prompts, API keys, raw error text, or request arguments.

- Enabled by default. `ZERO_METRICS=0` disables collection.
- Emits a `METRICS ` line to stderr, not the final-result stdout stream.
- Also appends metrics-only JSONL to `logs/pipeline-metrics.jsonl`, rotating at
  roughly 2 MB with one previous file. This makes app subprocess measurements
  observable even when their stderr is captured. `ZERO_METRICS_PATH` overrides
  the destination for tests.
- Account identifiers hash canonical config-directory paths. They distinguish
  accounts without printing raw paths or email addresses.
- `draftutil` budgets independent account configs separately within a process.
  API duration is end-to-end subprocess duration, never labeled CLI overhead.
- Jev metrics include pool activity and retry/backoff events. Failed HTTP status
  counts are separate from transport exceptions.

These changes are in the shared Python modules used by the app, `bin/zero run`,
and `run.sh`, not only the legacy scheduled shell script.

### 2. Exact learning reuse, with independent voice reuse

`learn.py` fingerprints the complete ordered input-signal snapshot, normalized
rejections, minimum threshold, implementation bytes, and provider configuration
including binary overrides. Unchanged inputs with an existing output skip the
rollup and preserve user edits. Equal event counts with different contents do
not skip.

Voice results have a separate exact prompt/model/provider key. A new restore or
rejection can rebuild deterministic preferences without another voice call.
Only nonempty successful voice results are cached. Failed generation neither
publishes a partial rollup nor marks those inputs complete. Byte-identical
output is not rewritten.

Concurrent learners use a stable sidecar lock. App rejections and final
publication share a separate short lock that is not held during generation.
Changes to learned text or rejections during generation abort publication, so
an in-flight rollup cannot reintroduce a just-rejected preference.

### 3. Validated caches rather than unconditional history skips

All candidates now reach exact decision-input validation, even when mailbox
history reports no changed candidates. Matching per-thread history IDs still
avoid metadata reads, and matching verdict fingerprints avoid Jev calls. Model
selection is now explicitly included in the threshold signature. Cached owner
identity is recomputed from the current owner's address.

Persisted negative sender evidence is re-probed on the next run. A reply in
another thread can make an old `False` wrong without changing this thread's
history ID. Same-run memoization/group probes remain, and positive evidence
retains its existing keep-biased TTL. This intentionally trades extra probes
for freshness. The benchmark below quantifies that cost.

Warm KEEP decisions must not trigger unconditional category reads/writes.
Full-thread reads can now carry both the union and intersection of message
labels. A no-op requires proof that **every** message has the target label and
**none** has an obsolete category. Legacy/newest-only cache rows cannot supply
this proof and fall back to an authoritative read. One fresh label-name map is
shared per run and updated after successful label creation. Cached metadata
only skips an already-correct label operation, never supplies labels for a
mutation. Missing or stale proof does not cause a write from cached state.

### 4. Equivalent metadata shared by dashboard and catch-up

`lib/metadata_cache.py` stores only full-thread `metadata` responses for the
identical `From`, `Subject`, `Date` header set. It is separate from classifier
rows and is never consumed by archive/send decisions.

- Canonical-account namespace, schema/header checks, current per-thread history
  ID equality, bounded age/size, atomic publication, and locked merges.
- Dashboard gets validation IDs from the listing it already performs.
- Catch-up preserves its original messages.list candidate selection. One bounded
  threads.list page validates possible cache hits. Missing IDs or candidates
  outside that page use live reads. This can cost an extra 10 units on cold runs.
- The stored version comes from the actual full response, not an earlier list
  snapshot. Changed mail, absent versions, corrupt files, and read failures do
  not serve stale data.
- The open-loop newest-message optimization is not misrepresented as equivalent
  full-thread data. Dashboard/catch-up sharing does not eliminate every read
  after the keeper stage.

### 5. Bounded Jev connection reuse

`lib/jev.py` leases at most 12 stdlib HTTPS connections exclusively, drains each
response before reuse, drops failed/closed sockets, and preserves typed request
and answer semantics. Existing ask-level backoff owns retries, capped at six
retries. `ask_many` remains ordered and failure-isolating, with at most 12 workers.
Proxy-configured HTTPS requests retain the urllib route and the concurrency cap.
`ZERO_JEV_POOL=0` disables pooling without changing classification.

Real local HTTP/1.1 transport tests verify socket reuse and server-requested
closure. TLS certificate verification remains the stdlib HTTPS default. There
was no live provider latency benchmark, so no handshake-time saving is claimed.

### 6. Shared-state and orchestration safety

- Unique temporary files, fsync, atomic replacement, stable sidecar locks.
- Thread-cache writes merge only changed keys and explicit deletions, avoiding
  unrelated lost updates from concurrent writers.
- Sync cursors and category-label history use locked read/modify/write operations.
- Malformed/future timestamps miss. Expired, malformed, partial, or failed history
  responses fall back rather than masquerading as an empty delta.
- Keeper and demote command entrypoints share per-config account locks, covering
  app and CLI child processes. Complete legacy scheduled runs are serialized.
- `run.sh` no longer loses failure exit codes inside pipeline subshell loops.
- App subprocess stderr is drained concurrently with a bounded diagnostic tail.
  Stdout is read in chunks with incremental decoding, so even a partial line
  cannot block beyond the deadline. Timed-out process groups are killed/reaped.
- Runtime metadata/thread caches and cursor state are gitignored.

## Measured offline outcomes

Run `ZERO_METRICS=0 python3 lib/benchmark_speed_pipeline.py`.

This executes the real keeper `main()` with `--execute --no-bulk` against 60
synthetic, already correctly labeled KEEP threads sharing one sender. Its fake
API rejects any mutation. Both cold and warm runs produce 60 kept, zero archive.
This is a reproducible call-count benchmark, **not a live latency estimate**.

| Scenario | Gmail calls | Jev classifications | Per-thread gets | Thread modifies |
|---|---:|---:|---:|---:|
| Cold, positive sender evidence | 69 | 60 | 60 | 0 |
| Warm, identical inputs | 5 | 0 | 0 | 0 |
| Warm, changed policy | 5 | 60 | 0 | 0 |
| Warm, negative sender revalidation | 7 | 0 | 0 | 0 |
| Reply elsewhere, unchanged target versions | 10 | 60 | 0 | 0 |

The identical-input fixture reduces Gmail calls by 64/69 (92.8%) and Jev calls
by 60/60. Warm estimated Gmail cost is 15 units versus cold 2,453 units for this
specific fixture. The negative-sender case costs two extra messages.list calls,
10 units, for the single shared sender and its failed grouping positive control.
Distinct senders and different positive-control results change that overhead.
Changed policy or reply evidence correctly invalidates all affected verdicts.

Other checked savings:

- Two identical learning runs make one voice request, not two, and preserve the
  output mtime. Changing a restore/rejection can reuse that same voice request.
- Identical dashboard metadata and subsequent catch-up use one full-thread read
  in the fixture, not repeated reads. Earlier owner messages still suppress
  catch-up, proving full-conversation equivalence.
- Four local HTTP requests use two TCP connections when the server explicitly
  closes after the third request. No TLS latency extrapolation is made.

Run each script in its own process to avoid their intentional module patches:

```bash
export ZERO_METRICS=0
for test in lib/tests/test_*.py; do python3 "$test" || exit 1; done
python3 lib/test_fix_profile_email.py
python3 lib/test_fix1_kept_threads.py
python3 lib/sync_state.py
python3 lib/learn.py --self-check
python3 lib/review_open_loops.py --self-check
python3 lib/benchmark_speed_pipeline.py
python3 -m compileall -q lib
bash -n run.sh bin/zero
git diff --check
```

`lib/tests/test_speed_pipeline.py` adds 27 offline tests covering exact learning
keys, same-count edits/rejections, missing outputs, provider changes, failed
voice generation, concurrent learners, real app rejections during generation,
full-thread equivalence, changed mail, account separation, missing/corrupt
metadata, no stale fallback, read/list version races, multi-process file writes,
cache merges/deletions, negative sender freshness, cursor expiry/partial errors,
failed atomic writes, large stderr, partial-line timeouts, scheduled failure
propagation, metric privacy/accounting, TCP reuse/closure, failed sockets, proxy
fallback, and complete cold/warm execute-path invalidation/category no-ops.
Existing key-storage and metadata-shape fixtures were updated for actual new
module dependencies and optional full-thread label evidence. Size-cap fixture
timestamps are now in the past, not future-dated.

Final verification: all 17 `lib/tests/test_*.py` scripts passed, including all 27
new speed-pipeline tests. The worker's full offline command above completed with
exit 0 in 66.71 seconds. The coordinator independently repeated the standalone
suite, additional self-checks, native app build/leak guard, and isolated packaged
imports plus source-byte parity for eight modules. All passed. The app was not
installed or restarted, and no live keeper run was initiated. Implementation and
tests are committed in `c14e0b2`.

Review used the loaded coding/review guidance directly because this execution
worker was instructed not to spawn children. The coordinator independently
reviewed and verified the diff. Findings resolved included warm category-write
amplification, shared label-map refresh, isolated-module dependencies, stderr pipe
saturation, and incomplete-line timeout blocking. The final simplification pass
retained separate full-thread metadata and classifier contracts rather than
merging superficially similar but unsafe cache paths.

## Deferred items and explicit limits

- **Cross-stage and cross-account pipeline overlap:** not enabled. Independent
  user quotas permit parallelism in principle, but project pressure, same-account
  subprocess budgets, and ordering need a measured scheduling design. Catch-up
  still has its existing digest-send behavior, so treating it as a harmless
  read-only background task would be misleading. State locks are groundwork,
  not proof that arbitrary overlap is safe.
- **Cross-process quota ledger:** not implemented. Account limiter state remains
  process-local. Account locks serialize keeper/demote CLI runs, not all panel
  actions, OAuth aliases for the same Gmail user, or external clients. Keep the
  conservative budget and existing ordering. Bulk page-all reconciliation still
  estimates observed page cost after the subprocess, not between remote pages.
- **Provider prompt caching/shared context:** unverified and unchanged. No vendor
  inquiry was sent, and threads were not batched into one judgment request.
- **Broad shared mailbox snapshot:** not implemented. Full-message history and
  newest-message classifier summaries are different contracts. Reusing them as
  interchangeable would be unsafe. Metadata absence simply costs live reads.
- **History-only early skipping:** disabled intentionally. A future skip must
  prove all external decision inputs and sender evidence current, not only that
  Gmail history is unchanged. Current warm category no-op evidence prevents the
  resulting validation pass from reintroducing per-thread writes.
- **Live speed/benefit:** unmeasured. There is no promised end-to-end runtime,
  cache-hit rate, bandwidth saving, or provider keep-alive hit rate. Existing
  positive sender evidence remains TTL-bounded and keep-biased, not immutable
  proof if sent mail is deleted. External edits that do not participate in local
  file locks and Gmail changes between validation and mutation remain existing
  consistency boundaries, not transactional guarantees.
- **UI redesign/progress changes and a direct Gmail HTTP replacement:** not part
  of this implementation. App progress remains intact, with its stream handling
  made resistant to stalls.

## Post-deploy monitoring and rollback

On the next ordinary user-authorized run, compare adjacent metrics-only records
by stage/account: `cache.thread`, `cache.verdict`, `cache.full_metadata`,
`learning.rollup`, `learning.voice`, `category.noop`, `jev.transport`, and Gmail
`quota_units_estimated`, `throttle_seconds`, `retries`, `command_failures`.
Expected: an unchanged warm workload needs fewer reads/classifications, while
policy or mail changes produce corresponding misses. Unexpected increases in
failures, throttling, or per-thread category mutations need investigation before
adding concurrency. Measurements are workload-dependent and should not be
compared across different candidate counts without normalization.

Use `ZERO_JEV_POOL=0` to isolate transport behavior, `ZERO_METRICS=0` to disable
logging, and existing `--no-cache` / `--full` options for bounded read-only
comparisons. Do not use `--execute` or the digest sender as a benchmark. Cache
files are disposable optimizations. Roll back the implementation commits if
regression evidence cannot be isolated safely. No production monitoring run was
started by this execution.
